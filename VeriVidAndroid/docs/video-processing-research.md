# VeriVid 모바일 영상 처리 조사

조사일: 2026-10-07. Android 공식 문서, 딥페이크 연구 논문, 공개 전처리 코드를 확인하고 현재 프로젝트 코드를 대조했다. 이 문서는 설계 제안이며, 실제 모델·서버 성능 측정이나 휴대폰 녹화 테스트 결과가 아니다. 앱 코드, 서버, API는 변경하거나 실행하지 않았다.

## 결론

현재 졸업작품에서는 Android 앱이 녹화·파일 확인·사용자 동의 후 전달을 맡고, 서버/모델 팀이 프레임 추출·얼굴 검출/정렬·추론을 맡는 방식을 권장한다. 모델 입력 규격이 확정되기 전에 앱에서 얼굴을 잘라내거나 프레임 수를 고정하지 않는다. 원본 파일을 선택할 수 있으면 재녹화보다 우선 제공하고, 화면 녹화는 다른 앱에서 보는 영상을 확보하는 보조 경로로 사용한다.

권장 흐름:

영상 선택 또는 화면 녹화 → 로컬 MP4 확인 → 길이·크기·재생 가능 여부 확인 → 사용자가 분석 요청 → 영상 파일 전달 → 서버에서 모델별 전처리·추론 → 결과 수신 → 기존 행동 신호등 표시

이 권장은 현재의 Android 클라이언트/백엔드/모델 담당 분리와 아래 자료를 종합한 설계 판단이다. 해당 자료가 이 프로젝트의 정확도나 속도를 보장하지는 않는다.

## 1. 현재 코드에서 확인한 사항

| 항목 | 현재 구현 |
| --- | --- |
| 화면 캡처 | `MediaProjection` + `VirtualDisplay` |
| 인코딩 | `MediaRecorder`, MP4 컨테이너, H.264 영상 |
| 녹화 설정 | 세로 최대 1080×1920 / 가로 최대 1920×1080, 비율 유지, 30fps, 목표 비트레이트 6Mbps |
| 소리 | 오디오 소스·인코더 설정 없음. 현재 녹화 파일에는 오디오 트랙을 만들지 않음 |
| 저장 | 앱 전용 외부 저장소의 `Movies/VeriVid/video_capture_날짜_시간.mp4` |
| 분석 | `VeriVidApp.kt`의 TODO와 타이머 기반 더미 화면 전환. 실제 추론·업로드 없음 |
| 저장 영상·사진 선택 | 현재 버튼은 분석 화면으로만 전환함. 실제 파일 선택/입력 연결은 아직 없음 |
| 최대 녹화 시간 | 코드에서 제한하지 않음 |

근거: `app/src/main/java/com/verivid/app/CaptureOverlayService.kt:193`, `:212`, `:241`; `app/src/main/java/com/verivid/app/ui/VeriVidApp.kt:117`, `:127`, `:299`.

녹화 설정은 실제 출력 영상의 품질·fps 보장이 아니다. 파일 메타데이터와 디코딩 가능 여부를 녹화 후 확인해야 한다. 현재는 `MediaRecorder.stop()` 예외를 무시하고 파일 존재/크기만 확인하므로 손상된 MP4를 완료 처리할 가능성도 점검해야 한다.

## 2. 처리 위치 비교

| 방식 | 장점 | 추가 부담/제약 | 이번 권장 |
| --- | --- | --- | --- |
| 앱에서 MP4 확보, 서버에서 전처리·추론 | 모델 입력과 전처리를 한곳에서 관리. 순서·타임스탬프·오디오를 유지하기 쉬움 | 영상 업로드 용량·네트워크 대기 | 1차 MVP |
| 앱에서 프레임/얼굴을 추출해 서버에 전달 | 입력을 엄격히 정하면 업로드량을 줄일 여지가 있음 | 샘플링·얼굴 정렬·회전·다중 얼굴 처리 규격 필요. 프레임 수/이미지 압축에 따라 오히려 용량 증가 가능 | 모델 팀 요구가 확정된 뒤 검토 |
| 휴대폰에서 모델 추론까지 수행 | 서버 없이 분석할 수 있는 경로 | 모델 변환·앱 용량·기기별 메모리/지연·발열 검증 필요 | 현재 범위 밖 |

DeepfakeBench 공개 코드는 영상에서 얼굴을 검출하고 정렬해 입력을 생성하며, 전처리 설정에서 프레임 샘플링 방식을 지정한다. 이처럼 전처리는 모델 파이프라인의 일부이므로 앱에서 임의의 JPEG 프레임이나 224×224 얼굴로 고정하면 안 된다. DeepfakeBench가 팀원의 실제 모델이라고 가정하지도 않는다. [공개 전처리 코드](https://github.com/SCLBD/DeepfakeBench/blob/main/preprocessing/preprocess.py), [설정 파일](https://github.com/SCLBD/DeepfakeBench/blob/main/preprocessing/config.yaml).

영상 전체가 너무 크면 먼저 짧은 분석 구간을 선택하도록 한다. 단일 이미지 기반 모델인지, 연속 프레임 모델인지, 영상·음성 모델인지에 따라 최종 전달 방식이 달라질 수 있다.

## 3. 녹화 길이·화질 제안

아래는 모델 성능을 측정하기 전의 출발점이며 확정 규격이 아니다.

- 사용자 안내는 얼굴이 잘 보이는 10~30초 녹화를 권장하고, 초기 테스트에서는 최대 30초 제한을 검토한다. 모델이 필요한 최소 길이는 별도 확인한다.
- 현재 1080p급 / 30fps / 6Mbps 설정을 우선 유지해 기준 샘플을 만든다. 720p나 더 낮은 비트레이트는 동일 영상의 탐지 결과를 비교한 뒤 선택한다.
- 6Mbps로 30초를 녹화하면 영상 데이터만 이론상 약 22.5MB다. 실제 파일 크기는 인코더·컨테이너 등에 따라 달라진다. 네트워크 전송 시간은 아직 측정하지 않았다.
- 이미 생성한 녹화 MP4는 기본적으로 재압축하지 않는다. 용량을 줄이는 첫 방법은 불필요한 녹화 길이를 줄이는 것으로 한다.
- 긴 저장 영상은 분석할 구간을 고르게 한다. 잘라낸 파일을 보낼 경우 구간 시작 시각을 함께 관리해 서버의 의심 시각을 앱 재생 위치에 정확히 대응시킨다.
- 파일 크기 제한은 백엔드가 허용하는 상한과 맞춘다. 임의의 50MB 같은 값을 실제 서버 규격처럼 사용하지 않는다.

FaceForensics++ 연구에서는 압축 수준에 따라 탐지 성능이 달라졌고, 압축·리사이즈가 조작 흔적을 약화할 수 있음을 설명한다. 따라서 화면 재녹화와 추가 압축이 우리 모델에도 영향을 줄 수 있다는 것은 합리적인 우려이며, 영향의 크기는 우리 모델로 직접 측정해야 한다. [논문](https://arxiv.org/html/1901.08971).

Android에서 자르기·크기 조절·형식 변환이 필요해지면 Jetpack Media3 Transformer를 검토한다. 가능한 경우 재인코딩 없이 압축된 샘플을 복사할 수 있지만, 모든 자르기가 무손실로 끝나는 것은 아니다. 업로드 파일을 자를 때에는 MP4 edit list로 앞부분을 숨기는 방식만 사용하지 않는다. 삭제한 듯 보이는 구간이 파일에 남을 수 있으며 서버 디코더도 다르게 해석할 수 있다. [Transformer](https://developer.android.com/media/media3/transformer), [변환·자르기 설명](https://developer.android.com/media/media3/transformer/transformations).

## 4. Android 캡처에서 꼭 확인할 점

화면 녹화는 다른 앱의 원본 영상 파일을 직접 받는 기능이 아니다. 화면에 재생된 모습을 다시 인코딩한다. 알림·자막·재생 UI·검은 여백 때문에 얼굴이 가려지거나 작아질 수 있다. 원본 파일과 같은 조건으로 간주하지 않는다.

Android 14 이상은 앱 한 개만 캡처하는 선택을 지원한다. 이를 안내하되, 사용자가 고른 앱/전체 화면과 캡처 크기 변경에 대응해야 한다. 녹화 재시작 시에는 기존 MediaProjection 토큰을 재사용하지 않고 새 동의를 받는다. 시스템 중지나 화면 잠금 때도 `onStop()`을 처리해야 한다. [MediaProjection 공식 문서](https://developer.android.com/media/grow/media-projection).

현재 코드는 `onStop()`에서 자원 해제만 하고 완료 파일을 확인 화면에 전달하지 않는다. 또한 `onCapturedContentResize()` 처리가 없고, 녹화 시작 후 메뉴가 자동으로 닫히지 않는다. 세로↔가로 전환, 시스템 중지, 전체 화면 녹화에서 플로팅 메뉴가 영상에 들어가는지를 실기기로 확인해야 한다. 여기서는 문제 후보만 기록했으며 수정하지 않았다.

캡처 보호 창은 화면이 비어 보일 수 있고, 다른 앱이 외부 오버레이 표시를 차단할 수도 있다. 따라서 모든 앱에서 녹화·플로팅 버튼이 작동한다고 안내하지 않는다. 차단된 경우 저장된 영상 선택 경로를 제공한다. [FLAG_SECURE 및 오버레이 차단](https://developer.android.com/security/fraud-prevention/activities).

## 5. 소리가 필요한 모델인지 먼저 확인

현재 파일은 영상만 담는다. 얼굴 영상 기반 모델은 이를 입력으로 쓸 수 있을지 팀원 규격을 확인하면 되지만, 입 모양과 음성의 일치 여부를 분석하는 모델은 이 입력만으로 동작하지 않는다.

다른 앱의 내부 소리 캡처는 Android 10 이상 `AudioPlaybackCapture`를 사용하며 오디오 권한과 상대 앱의 캡처 허용 정책 등 조건이 있다. 모든 앱의 소리나 통화 음성을 항상 녹음할 수 있다고 가정하면 안 된다. 휴대폰 마이크 소리를 녹음하는 것도 내부 재생 소리를 정확히 얻는 것과 다르다. [오디오 캡처 공식 문서](https://developer.android.com/media/platform/av-capture).

`VeriVidApp.kt:407`의 “입 모양과 음성 흐름 불일치”는 현재 더미 문구이다. 실제 모델이 해당 근거를 반환하지 않으면 표시하지 않아야 한다. Mouth/Eye/Temporal 점수와 heatmap도 모델의 실제 지원 항목만 표시한다.

## 6. 팀원과 합의할 전달·결과 규격

아래는 구현하지 않은 협의안이다.

1. Android → 백엔드: 파일 자체를 전달한다. 앱의 `/storage/...` 경로는 서버에서 읽을 수 없다. `multipart/form-data` 파일 업로드를 1차 방식으로 검토하고 MP4 여부와 실제 영상 코덱을 구분해 합의한다. [파일 전송 형식 표준](https://www.rfc-editor.org/rfc/rfc7578).
2. 메타데이터: 입력 출처(`screen_recording`/`selected_file`), 실제 길이, 해상도, 회전 정보, 오디오 유무, 선택 구간 시작 시각을 합의한다. 클라이언트 정보는 서버가 파일을 검사하는 일을 대체하지 않는다.
3. 분석 시간이 길면 업로드 완료 후 분석 작업 ID를 반환하고 상태를 조회하는 방식으로 분리한다. 앱에서는 업로드 진행률과 모델 분석 상태를 구분한다. 서버 진행률이 없으면 가짜 0~100% 대신 단계/대기 표시를 사용한다.
4. 결과: 분석 성공 여부, 위험 단계, 점수의 의미/범위, 실제 의심 구간 시각, 실제 근거 코드, 지원된 세부 지표, 모델 버전을 정한다. 시각 단위는 예를 들어 밀리초로 통일한다.
5. 얼굴 미검출·너무 작은 얼굴·검은 화면·손상 파일·소리 부족은 `LOW`로 처리하지 않는다. 위험 단계와 별개인 “분석하기 어려워요” 상태와 이유를 반환하게 한다.
6. LOW/MEDIUM/HIGH 경계는 모델 팀의 검증 자료를 기준으로 합의한다. 현재 더미 87%를 실제 진위 확률이나 판정 기준으로 삼지 않는다.
7. 취소·재시도·중복 업로드 방지·파일 보관/삭제 범위를 정한다. 현재 “기기에만 저장” 안내는 향후 실제 업로드가 도입될 때 전송 동의 및 보관 안내와 함께 수정해야 한다.

짧고 중단 가능한 백그라운드 전송에는 WorkManager를 검토할 수 있다. 사용자 요청으로 시작되는 긴 전송은 Android 14 이상 UIDT 작업도 검토한다. Android 16에서는 오래 실행되는 WorkManager 작업도 작업 할당량 영향을 받으므로 “WorkManager면 항상 끝까지 업로드된다”고 보장하지 않는다. 실제 MVP는 우선 분석 화면에서 전송·실패·취소를 처리하는 범위를 합의한다. [UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt), [장시간 WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running).

## 7. 모델 팀에 먼저 물어볼 질문

- 모델 이름/버전과 입력은 영상, 얼굴 이미지, 연속 프레임, 영상+음성 중 무엇인가?
- 프레임 수·샘플링 간격·시간 길이·얼굴 크기·정렬/정규화·다중 얼굴 선택 조건은 무엇인가? 이 전처리를 서버가 맡을 수 있는가?
- 오디오가 필수인가? 없으면 다른 모델로 처리할 수 있는가?
- 원본뿐 아니라 화면 녹화 영상에서도 평가한 적이 있는가?
- 프레임 점수/연속 구간/눈·입 점수/heatmap 중 실제로 반환 가능한 것은 무엇인가?
- 허용 파일 크기·코덱·최대 길이와 예상 분석 시간은 얼마인가?
- 판정 불가 상태, 위험 단계 경계, 결과 점수의 해석을 어떻게 정의할 것인가?

## 8. 실제 구현 전 검증 계획

정답 라벨과 사용 권한이 있는 동일 영상들을 원본 / 현재 설정의 화면 녹화 / 낮춘 해상도·비트레이트 조건으로 비교한다. 한 영상 결과만으로 화질을 결정하지 않는다.

| 검증 | 확인할 결과 |
| --- | --- |
| 입력 품질 | 파일 재생·디코딩 가능 여부, 실제 fps/시각, 얼굴 검출 비율·얼굴 픽셀 크기 |
| 탐지 영향 | 실제/조작 영상 각각의 오탐·미탐 변화, 반복 분석 점수 변동, 판정 불가 비율 |
| 앱 처리 | 권한 거절, 녹화 재시도, 너무 짧은 녹화, 화면 회전, 잠금/시스템 중지, 저장 공간 부족 |
